## 1. 무엇을, 왜 만드는가

헬스 기록, 식단, 인바디를 한곳에서 관리하고 그 기록을 수치와 그래프로 보여 주는 모바일 앱이다. 사용자는 기구·운동별로 세트, 횟수, 세트 간 휴식 시간을 기록하고, 먹은 음식과 인바디 수치를 입력한다. 앱은 이 기록으로 운동 성장과 칼로리 수지, 체성분 변화를 보여 준다. [결정]

**목적:** 헬스케어 풀스택 개발자 지원용 포트폴리오이며, 본인도 실제로 사용한다. 앱스토어 출시는 지금 목표가 아니고 완성 후 결정한다. [결정]

따라서 평가 기준은 기능 개수가 아니라 다음 네 가지다.
1. 실제로 배포되어 돌아가고, 다른 사람이 직접 확인할 수 있다. 실제 사용 기록은 사용 기기를 정한 뒤 쌓는다(5장 개발 환경 참고).
2. 앱, 서버, DB를 관통하는 설계를 직접 설명할 수 있다.
3. 건강 정보를 조심스럽게 다룬 흔적이 보인다.
4. 테스트와 자동화로 품질을 관리한다.

## 2. 목표와 범위

### 목표
- 운동 중 세트를 빠르게 기록하고, 인터넷이 끊겨도 기록을 잃지 않는다.
- 운동, 식단, 인바디 기록을 그래프와 수치로 보여 준다.
- 면접관이 설치 없이도 결과물을 확인할 수 있다(시연 영상, README, API 문서).

### 하지 않는 것
- 앱스토어·플레이스토어 출시, iOS 빌드 [제안 수락]
- 소셜 로그인, 삼성 헬스·애플 건강 연동 [제안 수락]
- 음식 사진 인식, 바코드 스캔, 인바디 결과지 자동 입력, AI 코칭 [제안 수락]
- 마이크로서비스, Redis, 메시지 큐 등 대규모 트래픽 대비 구조 [제안 수락]
- 다국어(한국어만), 태블릿 전용 화면, 한 계정의 여러 기기 동시 사용 [Claude 판단]
- 1차의 유산소 운동 기록(러닝머신 등). 근력 운동만 다룬다 [Claude 판단]

### 이렇게 되면 실패다
- 세트 하나 기록하는 데 운동 흐름이 끊길 만큼 오래 걸린다. 만든 본인도 안 쓰게 된다.
- 인터넷이 끊겨서 기록이 사라진다.
- 다른 사용자의 건강 정보가 보인다.
- 추정 소모 칼로리를 정확한 값처럼 보여 주거나, 질병 진단·치료처럼 보이는 표현을 쓴다.
- 시연 영상에서만 동작하고 실제 사용은 불가능하다.
- 기능은 많은데 전부 절반만 동작한다. 범위를 줄이더라도 있는 기능은 끝까지 동작해야 한다.

## 3. 기능 범위

### 1차: 반드시 완성 [제안 수락]

**계정**
- 이메일·비밀번호 가입, 로그인, 로그아웃
- 가입 시 건강 정보 수집 동의(별도 항목). 동의 없이는 가입 불가
- 계정 삭제: 앱 안에서 즉시 삭제하고 관련 기록을 모두 지운다

**운동 기록**
- 기본 운동 목록(운동명, 기구, 부위) 제공, 검색, 사용자 정의 운동 추가
- 운동 시작 → 운동 선택 → 세트 기록(무게, 횟수) → 운동 종료
- 세트 완료 시 휴식 타이머 자동 시작, 타이머가 끝나면 진동·알림
- 같은 운동의 지난번 무게와 횟수를 표시하고, 입력칸의 기본값으로 채움
  - 기본값은 지난 세션의 같은 번호 세트 값이다. 오늘 직전 세트를 그 기본값과 다르게 바꿨거나 지난번에 같은 번호 세트가 없으면 오늘 직전 세트 값을 쓴다 [Claude 판단]
  - 휴식 타이머 기본값은 90초이고, 화면에서 ±30초로 조절한다. 마지막으로 쓴 길이는 폰에만 저장하며 운동별로 따로 두지 않는다 [Claude 판단]
- 지난 운동 기록 조회, 수정, 삭제
- 인터넷이 끊겨도 기록 가능, 연결되면 자동 동기화

**운동 분석**
- 운동별 최고 무게, 추정 1RM, 볼륨 변화 그래프(기간 선택: 4주, 12주, 전체)
- 날짜별 운동 내역과 평균 휴식 시간

**식단**
- 아침, 점심, 저녁, 간식별 음식 기록
- 공공 식품영양성분 데이터 검색, 직접 입력 음식 추가
- 섭취량(g) 입력 시 칼로리, 탄수화물, 단백질, 지방 자동 계산

**칼로리 분석**
- 날짜별 섭취 칼로리, 운동 추정 소모 칼로리, 차이(섭취 − 운동 소모)
- 소모 칼로리에는 항상 "추정치" 표시

**인바디**
- 측정일별 직접 입력. 체중은 필수, 골격근량, 체지방량, 체지방률, 기초대사량, 메모는 선택
- 항목별 변화 그래프, 기록 수정·삭제

**홈**
- 오늘의 운동, 섭취·소모 칼로리, 최근 체중 요약과 운동 시작 버튼

### 2차: 1차 완성 후, 하나씩 추가 [제안 수락]
- 루틴 저장과 불러오기
- 목표 설정(목표 체중, 하루 칼로리)과 달성률
- 부위별 운동량 분석, 최고 기록 달성 표시
- 주간 리포트
- 유산소 운동 기록 [Claude 판단]
- 내 데이터 내보내기(JSON), 건강 정보 접근 기록 [Claude 판단: 헬스케어 직무 어필 요소]

### 3차: 나중에 검토 [제안 수락]
헬스 앱 연동, 사진·바코드 입력, 인바디 결과지 자동 입력, AI 코칭, 스토어 출시.

## 4. 계산 규칙

모든 계산은 서버 한곳에 두고 단위 테스트한다. 운동 중 "지난 기록 표시"만 앱이 저장해 둔 데이터를 쓴다. [Claude 판단]

| 수치 | 계산식 | 규칙 |
|---|---|---|
| 볼륨 | Σ(무게 kg × 횟수) | 맨몸 운동은 무게 0이므로 볼륨 대신 총 횟수를 보여 준다 |
| 추정 1RM | 무게 × (1 + 횟수 ÷ 30) (Epley 공식) | 횟수 1이면 무게 그대로. 횟수 13 이상 세트와 무게 0 세트는 제외 |
| 휴식 시간 | "다음 세트 시작"을 누른 시각 − 세트 완료 시각 | 앞 세트에 저장. 누르지 않으면 비워 두고 평균에서 제외. 수정 가능 |
| 운동 소모 칼로리 | MET 5.0 × 체중 kg × 운동 시간(시간) | 운동 시간은 시작~종료. 체중은 운동일 이전의 가장 최근 인바디 값. 없으면 계산하지 않고 체중 입력을 안내 |
| 음식 영양소 | 100g당 값 × 섭취량 ÷ 100 | 기록 시점의 값을 저장해, 음식 정보가 바뀌어도 과거 기록은 유지 |
| 칼로리 차이 | 섭취 − 운동 소모 | 기초대사량은 포함하지 않으며 화면에 그렇게 밝힌다 |

- MET 5.0은 근력 운동 전체에 쓰는 고정값이다. 서버 상수 하나로 두고, 나중에 조정할 수 있게 한다. [Claude 판단]
- "오늘"의 기준은 Asia/Seoul이다. 시각은 UTC로 저장하고, 날짜 집계만 이 시간대로 계산한다. [Claude 판단]
- 수치 단위는 kg, g, kcal로 고정한다. [Claude 판단]

### 개발 환경과 사용 기기
- 먼저 개발에 집중하고, 서버 배포는 뒤로 미룬다. 개발 중에는 노트북의 로컬 DB를 쓴다. [결정]

- 개발 중 데이터는 테스트용이며 지워도 된다. 그래도 스키마 변경은 처음부터 Flyway로 관리한다. [Claude 판단]
- 사용자의 폰은 iPhone이고 노트북은 Mac이 아니다. [결정]

- 지원 시기는 미정이다. 따라서 미리 기능을 줄이지 않고, 12장 순서대로 진행한다. [결정]

## 6. 데이터 구조

모든 사용자 데이터는 `user_id`를 가지며, 서버는 항상 로그인한 사용자 기준으로만 조회한다. 사용자 삭제 시 함께 삭제된다. [Claude 판단]

| 테이블 | 주요 항목 |
|---|---|
| users | id, email(고유), password_hash, nickname, created_at |
| consents | user_id, type, version, agreed_at |
| refresh_tokens | user_id, token_hash, expires_at, revoked_at |
| exercises | id(UUID, 사용자 정의 운동은 앱에서 생성), owner_user_id(null이면 기본 제공), name, equipment, body_part, hidden_at |
| workout_sessions | id(UUID, 앱에서 생성), user_id, started_at, ended_at, memo, updated_at |
| workout_sets | id(UUID), session_id, exercise_id, order_no, weight_kg, reps, completed_at, rest_seconds |
| foods | id, owner_user_id(null이면 공공 데이터), name, kcal/carb/protein/fat(100g당), source |
| meal_entries | id, user_id, eaten_on(날짜), meal_type, food_id, food_name, grams, kcal, carb_g, protein_g, fat_g(기록 시점 값) |
| body_measurements | id, user_id, measured_on(날짜), weight_kg, skeletal_muscle_kg, body_fat_kg, body_fat_pct, bmr_kcal, memo. (user_id, measured_on) 고유 |

- 삭제된 사용자 정의 운동이 과거 기록을 깨지 않도록, 운동은 숨김 처리만 한다(`hidden_at`). [Claude 판단]
- 기본 운동 목록은 많이 쓰는 근력 운동 50개 안팎을 Flyway로 넣는다. 내용은 구현 시 작성한다. [Claude 판단]

## 7. 오프라인과 동기화 [Claude 판단]

운동 기록만 오프라인을 지원한다. 식단과 인바디는 나중에 입력해도 되므로 온라인 전용으로 두고, 실패 시 오류를 안내한다.

1. 진행 중인 운동은 먼저 폰(SQLite)에 저장하고, 세트마다 바로 저장한다.
2. 앱이 세션 UUID를 만들고, 운동 종료·수정 시 세션 전체를 `PUT /workouts/{id}`로 보낸다. 같은 요청을 여러 번 보내도 결과가 같다.
3. 실패하면 "미전송" 표시를 남기고, 앱 실행·연결 복구 시 다시 보낸다.
4. 한 사람이 기기 하나로 쓰는 전제이므로, 충돌은 마지막 수정 우선으로 처리한다.
5. 앱을 강제 종료해도 진행 중인 운동이 복구된다.
6. 휴식 타이머는 "끝나는 시각"을 저장해 계산하므로, 백그라운드에서도 시간이 어긋나지 않는다.

오프라인에서 되는 범위는 아래까지로 한정한다. 폰에 서버 전체 복사본을 두지 않는다.

- **가능:** 운동 시작·기록·종료, 운동 목록 검색, 사용자 정의 운동 추가, 지난 기록 기본값 표시, 아직 보내지 않은 운동의 수정·삭제
- **온라인 전용:** 전송 완료된 과거 운동의 조회·수정·삭제, 모든 통계. 그래서 삭제 요청은 재전송 대상이 아니며, 삭제한 운동이 재전송으로 되살아나지 않는다
- **캐시:** 운동 목록과 운동별 지난 기록을 로그인 시와 앱 실행 시 받아 폰에 저장한다. 재설치나 기기 변경 후에도 다음 로그인 때 다시 받는다
- **전송 순서:** 새 사용자 정의 운동을 먼저 보내고 운동 세션을 보낸다

폰에 저장하는 건강 정보의 암호화는 1차에 포함하지 않는다. 앱 전용 저장 공간과 OS 보호에 의존하며, 출시를 결정하면 다시 검토한다. [Claude 판단]

## 8. API 개요 [Claude 판단]

세부 형식은 구현 시 정하고 Swagger로 문서화한다.

```
POST   /api/v1/auth/signup (초대 코드 포함) | login | demo-login | refresh | logout
GET    /api/v1/me            DELETE /api/v1/me

GET    /api/v1/exercises            PUT /api/v1/exercises/{id}  (사용자 정의 운동)
GET    /api/v1/exercises/last-performance  (운동별 최근 세션의 세트, 일괄 조회)

PUT    /api/v1/workouts/{id}        (세션 + 세트 전체 저장)
GET    /api/v1/workouts?from=&to=   GET | DELETE /api/v1/workouts/{id}

GET    /api/v1/foods?query=         POST /api/v1/foods
GET    /api/v1/meals?date=          POST /api/v1/meals
PUT | DELETE /api/v1/meals/{id}

GET    /api/v1/body-measurements?from=&to=   POST /api/v1/body-measurements
PUT | DELETE /api/v1/body-measurements/{id}

GET    /api/v1/stats/daily?date=
GET    /api/v1/stats/exercises/{id}?from=&to=
```

다른 사용자의 데이터를 요청하면 존재 여부를 알 수 없도록 404로 답한다.

## 9. 화면 [Claude 판단]

Android 세로 화면 기준이며, 하단 탭은 홈, 운동, 식단, 인바디 네 개다.

- **로그인·가입:** 건강 정보 동의 포함
- **홈:** 오늘의 요약, 운동 시작
- **운동 진행(가장 중요):** 한 손으로 쓰는 큰 버튼. 지난 기록이 기본값으로 채워져 있어, 그대로면 "세트 완료" 한 번으로 기록된다. 완료 후 휴식 타이머가 화면에 나오고 "다음 세트 시작"을 누른다
- **운동 탭:** 지난 기록 목록·상세, 운동별 성장 그래프
- **식단 탭:** 날짜별 끼니, 음식 검색·추가, 칼로리·영양소 합계
- **인바디 탭:** 최신 수치, 항목별 그래프, 입력
- **설정(홈에서 진입):** 로그아웃, 처리방침 보기, 계정 삭제

디자인 세부 사항은 구현 시 정하되, 먼저 운동 진행 화면의 시안을 만들어 사용자 확인을 받는다.

## 10. 보안과 건강 정보 [제안 수락 + Claude 판단]

- HTTPS 전용, 비밀번호 BCrypt, 비밀값은 환경 변수로 관리하고 저장소에 넣지 않는다.
- 모든 조회·수정·삭제에 소유자 검사를 적용하고, 다른 사용자 접근 차단을 통합 테스트한다.
- 로그에 건강 수치, 토큰, 비밀번호를 남기지 않는다.
- 건강 정보 동의의 버전과 시각을 기록하고, 간단한 처리방침을 앱에서 볼 수 있게 한다.
- 계정 삭제 시 데이터를 실제로 삭제한다. 백업은 7일 보관 후 폐기한다.
- 공개 시연용으로 다른 사람의 실제 건강 정보를 받지 않는다. 가입은 초대 코드(서버 환경 변수 값 하나, 별도 테이블 없음)가 있어야 가능하며, 코드는 본인만 쓴다.
- 시연은 가상 데이터가 든 데모 계정으로 한다.
  - 로그인 화면의 "데모로 둘러보기" 버튼으로 들어간다.
  - 데모 계정은 읽기 전용이다. 서버에서 데모 사용자의 모든 쓰기 요청(계정 삭제 포함)을 공통으로 막는다.
  - 서버 작업으로 매일 데모 데이터를 오늘 날짜 기준으로 다시 만들어, 홈과 4주 그래프가 비지 않게 한다.
  - 같은 서버와 DB를 쓰며, 본인 데이터와는 소유자 검사로 분리한다.
  - 쓰기 동작은 시연 영상으로 보여 준다.
  - Swagger는 문서 열람용으로 공개하며, 데모 토큰으로는 조회만 된다.
- 앱 내 문구는 기록과 참고 수치로 한정하고, 진단·치료·처방처럼 보이는 표현을 쓰지 않는다.

## 11. 공공 음식 데이터 [제안 수락 + Claude 판단]

식품의약품안전처 식품영양성분 데이터베이스(공공데이터)를 내려받아 `foods` 테이블에 넣는 가져오기 작업을 한 번 실행한다. 앱에서 외부 API를 직접 호출하지 않는다. 사용 조건과 출처 표기는 내려받을 때 확인해 앱과 README에 반영한다. 실제 데이터 사용이 막히면 직접 입력과 소규모 샘플 데이터로 대체한다.

## 12. 진행 단계

각 단계는 앱, 서버, DB가 함께 동작하는 상태로 끝낸다.

| 단계 | 내용 | 완료 기준 |
|---|---|---|
| 0. 기반 | Git, 폴더 정리, Android 에뮬레이터 확인, 로컬 DB용 Compose, Spring Boot + Flyway, CI, 가입·로그인 | 앱에서 가입하고 로그인되며, 소유자 검사 틀이 있음 |
| 1. 운동 기록 | 운동 목록, 세트 기록, 휴식 타이머, 오프라인 동기화 | 에뮬레이터에서 운동 한 번을 끝까지 기록하고, 인터넷 차단 후 복구해도 동기화됨 |
| 2. 운동 분석 | 볼륨, 1RM, 휴식 통계, 그래프 | 입력한 기록이 그래프로 보임 |
| 3. 인바디 | 입력, 그래프 | 체중이 칼로리 계산에 쓰일 준비가 됨 |
| 4. 식단·칼로리 | 음식 데이터, 식사 기록, 칼로리 분석 | 하루 칼로리 차이가 보임 |
| 5. 마무리 | 홈, 설정, 계정 삭제, 처리방침 | 1차 기능 전체 동작 |
| 6. 배포·공개 | 실사용 기기 결정, 서버 배포, 백업, 데모 계정, APK, README, 영상 | 다른 사람이 링크만으로 확인 가능 |
| 7. 실사용 | 정한 기기로 실제 헬스장에서 사용, 불편 개선, 2차 기능 선택 | 개선 사례를 README에 기록 |

## 13. 완료 기준

- 운동 한 번을 앱만으로 끝까지 기록할 수 있다(6단계 전에는 에뮬레이터, 7단계에는 실제 기기와 헬스장).
- 지난번과 같은 세트는 추가 입력 없이 한 번의 터치로 기록된다.
- 비행기 모드로 운동을 기록하고 앱을 재시작해도 기록이 남아 있으며, 연결 후 서버로 전송된다. 재전송해도 중복되지 않는다.
- 사용자 A가 사용자 B의 데이터에 접근할 수 없음이 자동 테스트로 검증된다.
- 계산 규칙(4장)이 경계 사례까지 자동 테스트된다.
- 계정 삭제 후 해당 사용자의 데이터가 DB에 남지 않음이 테스트로 검증된다.
- HTTPS 서버, 설치 가능한 APK, Swagger, 데모 계정, 1~2분 시연 영상, README(설계도와 선택 이유)가 공개되어 있다.
- CI가 모든 커밋에서 테스트를 실행한다.
